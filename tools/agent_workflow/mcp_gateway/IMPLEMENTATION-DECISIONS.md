# MCP-GATEWAY-SPEC-001 — A2 implementation decisions

**Mission:** M-EPAP-MCPGW-002, round 1
**Built from:** `missions/M-EPAP-MCPGW-002/PLAN.md`, whose operative content is the spec. It builds on `tools/agent_workflow/mcp_auth/` (the fabric) and `tools/agent_workflow/retrieval/` (loop 1).

The code does not amend the spec. Where the plan leaves a choice open, the choice below fails closed and is recorded here so A1 or HITL can reject it.

## Layout

| File | Role |
|---|---|
| `protocol.py` | Newline-delimited JSON-RPC 2.0 on stdio; `initialize`, `notifications/initialized`, `ping`, `tools/list`, `tools/call`, and nothing else |
| `tools.json` | The tool catalog as data (`mcp-gateway-tools-v1`) |
| `session.py` | The launcher's session file, and the per-session policy overlay |
| `server.py` | `Gateway`: catalog loading, fabric requests and decisions, retrieval, the evidence log |
| `__main__.py` | `python3 -m mcp_gateway --root CHECKOUT --session FILE --evidence-dir DIR` |
| `../tests/test_mcp_gateway.py` | Vectors P1–P7 as `test_vector1_…` to `test_vector7_…`, plus hardening cases |

There is no `__init__.py`: `mcp_gateway` is a namespace package, like the earlier legs.

## Resolutions

1. **Where policy and registry come from.** The fabric policy (`mcp_auth/policy.json`) and the corpus registry (`retrieval/corpus.json`) are read from the gateway's own tree (the tooling tree the dispatcher runs it from), never from `--root`. The agent can edit its checkout, so reading policy from there would let an agent widen its own grants. Retrieval reads documents only under `--root`. Tests may pass another policy, catalog or registry to `Gateway(...)`; the CLI cannot.
2. **Refusal to start.** The gateway exits 2 with the reason on stderr, and serves nothing, when: `--root` is not a directory; `--evidence-dir` is not a directory, is a symlink, or lies inside the checkout; the policy is unavailable or malformed; the registry is unavailable or malformed; or the catalog is malformed. The catalog is malformed if a tool names an action the policy does not know, an action of kind `write` or `execute`, an action outside its resource's `read` set, an unknown resource, a corpus scope that does not resolve in the registry, an unknown `retrieval_method`, or an input schema outside the subset in resolution 9. A malformed policy refuses to start instead of denying every call with stop 12, because without a policy the catalog's read-only check cannot be made.
3. **An invalid session does not stop the server.** It makes `tools/list` empty and every `tools/call` DENY with stop 13. A session is invalid when the file is missing, unreadable, a symlink, larger than 64 KiB, not JSON (duplicate keys and non-integer numbers count as malformed), has a missing or unknown key at either level, has an `authority_ref` other than `MISSION-ROUTER-001`, a `base_sha` that is not 40 lowercase hex, a `round` below 1, an empty or repeating `resources` list, or time bounds that are not integer epoch seconds with `issued_at < expires_at`. It is also invalid when its path, taken as given or resolved, lies inside the checkout root, or when the overlay cannot be built (resolution 5).
4. **Session times are integer epoch seconds**, the fabric's own unit, so they pass into the fabric request unchanged. An expired or not-yet-valid session is checked by the gateway at the server clock before the fabric is asked. That gives stop 13 even for a seat the policy does not know, where the fabric would report stop 2 first. A session the gateway cannot bind gets a DENY in the fabric's own record format (`mcp_auth.records.make_record`): failed step `identity`, stop 13, `cleared: [12]` (the policy loaded), and the shipped policy's version and digest (or the overlay's, when one was built).
5. **The overlay** is the validated shipped policy plus exactly one `missions[<mission id>]` entry, `{authority_ref: "MISSION-ROUTER-001", resources: <session resources>, approvals: {restricted: [], credential: [], runtime: []}}`, and the mission id appended to `authority_refs["MISSION-ROUTER-001"].missions`. It is built in memory and never written. It must pass `mcp_auth.policy.validate`. If it does not, the session is invalid. The session is also invalid if the policy has no `MISSION-ROUTER-001` reference, if the mission id is already in the policy, or if a session resource is not in the policy. Approvals are always empty, so restricted or credential-bearing material and runtime implications stay denied (stops 7–9).
6. **Fabric request.** `principal` is `{id: <session principal>, kind: "agent"}`: the gateway serves agent seats only, so a principal of another kind fails the fabric's identity step (stop 2). The fabric session is `{id, principal, acting_identity, mission, issued_at, expires_at}` from the session file. Its `id` is `session-` plus the first 16 hex digits of the SHA-256 of the session file's bytes. `resource.class` comes from the policy. `evidence.can_produce` is `["audit_record"]`, because the gateway writes the decision log before anything runs. `implicates` is `[]`. `connector.credential_bearing` is `false`. `request_id` is `<mission>.r<round>.call-<n>`, numbered per server process.
7. **Connector capabilities are stated per resource.** The plan gives the connector's capabilities as "the listed tools' actions". The fabric's stop 1 compares them with the role's grants on the *requested resource* only. A list that mixed the `rag` and `epap` tools would therefore deny every call with stop 1 for a session holding both resources. The gateway states the actions of the listed tools whose resource is the one being called, plus the action being requested. The requested action is still decided at `action_grant`, and an action the grants do not cover can never pass stop 1.
8. **`tools/list` probes each catalog tool** with a fabric request whose connector states only that tool's action, at the server clock, and lists the tool only on ALLOW. These probes authorize nothing and run nothing, so they are not written to the evidence log. Every `tools/call` is decided again, and that decision is logged. A `tools/call` for a catalog tool that is not listed goes to the fabric and comes back as its DENY (for example stop 4 for a resource outside the session). A `tools/call` for a name not in the catalog has no action to decide. It is a tool error with disposition `REFUSED`, logged as a `refusal` entry, and nothing runs.
9. **Tool arguments.** Input schemas use one fixed subset: an object with `additionalProperties: false`, declared `properties`, optional `required` and `minProperties`. Each property is a known argument: `query` (the claim text), or a retrieval constraint (`document_id`, `path`, `location`, `status`, `title`, `date`, `alias` as strings, and `keywords` as a non-empty list of strings). All arguments other than `query` become the retrieval request's `constraints`. `corpus_scope` and `retrieval_method` come from the catalog, never from the caller: `search` pins `lexical`, and the other tools run the full hierarchy. Arguments are checked after an ALLOW. A mismatch is a JSON-RPC `-32602` and runs nothing. The ALLOW record stays in the log with no `RETRIEVAL` link, so every decision is recorded and no retrieval is claimed.
10. **Order of a call:** decide, append the decision, and stop on DENY. Then check the arguments, run retrieval, append the `RETRIEVAL` link, and only then return the result. If the decision cannot be appended, the call is refused and nothing runs. If retrieval raises, the call is a tool error and returns nothing, logged as `retrieval_error`. If the link cannot be appended, the result is withheld. A retrieval abstention (for example `ACL_SCOPE_FAILURE`) is a successful call whose result says it abstained: retrieval's ACL still applies under an ALLOW.
11. **Evidence log.** `decisions.jsonl` in `--evidence-dir` holds one JSON object per line. A `decision` entry carries `request_id`, `tool`, `mission` (`id`, `authority_ref`, `base_sha`, `round`; null without a valid session), `session`, the fabric `request` (null when no session could be loaded), the `mcp-auth-decision-v1` `record`, and its `MCP_AUTH_DECISION` link material (`mcp_auth.records.link_material`). A `retrieval` entry carries the same `request_id`, `tool` and `mission`, the `retrieval_request`, and the `RETRIEVAL` link material (`retrieval.retrieve.evidence_link`). `refusal` and `retrieval_error` entries are as in resolutions 8 and 10. The record format is the fabric's and is not extended, so `base_sha` and `round` sit beside the record in the entry. Links are not signed here; signing belongs to the dispatcher's evidence handling.
12. **Tool results.** ALLOW: `isError: false`, and `structuredContent` `{disposition: "ALLOW", request_id, tool, grant, result, citations}`, with the same object as JSON text in `content`. DENY: `isError: true`, and `structuredContent` `{disposition: "DENY", request_id, tool, failed_step, stop_condition, reason}`, with text naming the failed step and the stop condition. A DENY is never turned into a narrower ALLOW, and no read is substituted for a denied write.
13. **Protocol.** `initialize` answers protocol version `2025-06-18` whatever version the client asks for. It requires `protocolVersion` to be a string, and `capabilities` and `clientInfo` to be objects when present. The server states `capabilities: {tools: {listChanged: false}}`, `serverInfo: {name: "governed-retrieval", version: "MCP-GATEWAY-SPEC-001"}`. Requests are not refused before `initialize`, because each call is decided by the fabric whatever the lifecycle state. The server answers:
    - a line that is not UTF-8 JSON (including `NaN`/`Infinity`) with `-32700`;
    - a non-object (batches are not part of `2025-06-18`), a wrong `jsonrpc`, a missing or non-string method, or an id that is not a string or integer with `-32600`;
    - an unknown method with `-32601`;
    - params that are not an object, a `tools/call` without a string `name` or with non-object `arguments`, or a `tools/list` cursor (no cursors are issued) with `-32602`;
    - a defect in the server itself with `-32603`.

    Notifications are never answered. Incoming responses are ignored, because the server sends no requests. Blank lines are skipped. The loop serves until end of input.
14. **Shipped data changes are exactly D1 and D3.** `mcp_auth/policy.json` gains `MISSION-ROUTER-001` (kind `HITL`), seats `a2`/`a3`, and the four read-only `G-MISSION-*` grants, which mirror the `G-BUILDER-*`/`G-REVIEWER-*` grants except for the authority reference. `retrieval/corpus.json` gains `corpus:epap-evidence`. `mcp_auth/IMPLEMENTATION-DECISIONS.md` resolution 13 ("shipped policy binds no identity") describes the policy before D1. That file is outside this loop's build scope and is left unchanged; the shipped policy still has no missions, so with the shipped data alone every request is still denied until a session overlay admits one.
