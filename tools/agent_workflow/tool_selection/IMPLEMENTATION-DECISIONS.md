# GOVERNED-TOOL-SELECTION-SPEC-001 — A2 implementation decisions

**Mission:** M-EPAP-TOOLSELECT-001, round 2 (fixes the round-1 finding on P2)
**Built from:** `missions/M-EPAP-TOOLSELECT-001/PLAN.md`, which restates the spec's operative content, with the parent doctrine `governance/doctrine/L1-MCP-RAG-EPAP-GOVERNED-TOOL-SELECTION-PRIMITIVE-001.md` as reference. The spec text itself is not in the checkout.

The code does not amend the spec. Where the plan leaves a choice open, the choice below fails closed and is recorded here so A1 or HITL can reject it.

## Layout

| File | Role |
|---|---|
| `select.py` | The pipeline: `select(request, matrix, registry)` and `select_files(request, registry_path, matrix_path)` |
| `matrix.py` | Matrix schema, strict validation and loading |
| `matrix.json` | The shipped role tool-surface matrix (doctrine §4 writer / reviewer / router rows) |
| `registry.py` | Candidate registry envelope and per-entry checks; the registry is an input file |

There is no `__init__.py`: `tool_selection` is a namespace package.

## Resolutions

1. **Order.** Three prechecks run first: `matrix` (missing or malformed), `registry` (malformed envelope), `request` (not an object, unknown fields, no `request_id`, or no SOT mission authority: `mission.id` and `mission.authority_ref`). Then the spec's eight steps in order. Each of the first four steps resolves its selection-level input before judging candidates: `need_detection` the tool needs, `role_admission` the acting role, `boundary_filtering` the mission repo and scope, `mission_type_filtering` the mission type. If any of these cannot be resolved, the result is `STOP_AND_FAIL_CLOSED` with an empty surface. Every candidate is then listed as DENY with the stop reason.
2. **Need detection.** The request carries `needs`, the capabilities the mission needs. `[]` means the mission is answerable from closed mission context. The disposition is then `NO_TOOL_REQUIRED` and the surface is empty. A need naming a capability outside the matrix catalog is a stop. Need detection is a selection-level decision. Narrowing to the needed capabilities happens per candidate only after role admission has judged it (see item 4): a candidate on the row's admitted surface whose capability is not needed is denied at `role_admission` as `NOT_NEEDED`.
3. **Deny on resolved facts only.** A filtering step denies a candidate only on facts it can resolve. If a step cannot decide (unknown capability, malformed resource), the candidate passes on with that confidence signal unresolved. It can still be denied by a later step, but never admitted. Denials may use registry metadata, because a denial only narrows. Admission needs every signal resolved.
4. **Separation rule.** On a read-only row (reviewer, router), any candidate whose catalog class *or* declared class is `write`, `execute` or `elevated` is denied at `role_admission` with the row's `separation_rule`: `WRITER_REVIEWER_SEPARATION` for the reviewer, `ROUTER_NO_MUTATION` for the router. This check runs first for every candidate and ignores the needs list. A reviewer or router request with read-only needs, or with no needs at all, therefore still denies each mutation candidate under its separation rule. Per candidate, the order is: separation rule, `NO_TOOL_NEED` (when `needs` is `[]`), `ROLE_BLOCKED`, `ROLE_NOT_ADMITTED`, `NOT_NEEDED`. After that come the boundary, mission-type and evidence-class filters. *(Round 2: round 1 ran `NOT_NEEDED` before the separation check, so unneeded mutation candidates were denied without the rule being named.)*
5. **Separation is in the data.** `matrix.py` rejects a matrix in which the reviewer or router row is not read-only, a read-only row admits a mutation class, any row or mission type admits `elevated`, a capability is both admitted and blocked, or an admitted capability's class is outside its row's evidence classes. No role logic lives in the code.
6. **Matrix rows.** The rows follow the doctrine §4 lists. Writer: `file_edit`, `branch_create`, `commit`, `pr_create`, `local_test`, `artifact_create`, `doctrine_draft`, `architecture_map`. Reviewer: `repo_read`, `diff_review`, `evidence_inspect`, `doctrine_lookup`, `benchmark_review`, `disposition_draft`. Router: `artifact_lookup`, `doctrine_lookup`, `evidence_class_routing`, `citation_extract`, `corpus_search`. The doctrine's restricted lists are each row's `blocked` table, with reasons. `disposition_draft` is `draft`-class: it produces a draft, it does not mutate. Final `review_disposition`, `merge`, `self_approval`, `credential_access` and `production_runtime` are `elevated`, and no row admits them. There is no self-review exception.
7. **Boundary.** The mission scope has `read` and `write` path lists. These are clean relative paths, and `"."` is the whole repo. A read- or draft-class candidate must fall under `scope.read`. Any other class, a candidate whose capability is unknown, or a candidate whose declared class disagrees and is a mutation class must fall under `scope.write`. A different repo is denied as `REPO_BOUNDARY`. Matching works on path components, so `foo_evil` does not match `foo`.
8. **Mission types.** CAPTURE and PLAN admit read, draft and write. IMPLEMENT also admits execute. VERIFY and CLOSEOUT admit read and draft.
9. **Confidence.** The five signals are `role_resolved`, `mission_type_resolved`, `resource_in_scope`, `registry_entry_valid` and `evidence_class_resolved`. `registry_entry_valid` means the entry has exactly the entry fields, a unique well-formed name, a catalog capability, and a well-formed `input_schema`. `evidence_class_resolved` means the declared class equals the catalog class for the capability. The score is recorded as the string `"<n>/5"`, and the threshold as the matrix string (`"1.0"`), because canonical JSON has no floats. A candidate is admitted only if every signal is resolved *and* the score meets the threshold. A threshold below 1.0 therefore cannot admit a candidate with an unresolved signal.
10. **Fallback cannot widen.** `fallback(pre_fallback, unresolved)` builds its result by filtering `pre_fallback`. Each routed candidate gets the route of its first unresolved signal, taken from the matrix `fallback_routes` table: `BOUNDED_CLARIFICATION` for candidate signals, `HITL_GATE` for role and mission type. The disposition is `BOUNDED_CLARIFICATION`, and the narrowed surface stands.
11. **Fail-closed step.** The last step checks `admitted ⊆ pre_fallback`. It then re-checks every admitted tool independently against the row, the mission type, the registry entry and the boundary. Any violation stops the selection with an empty surface, as does any unexpected exception in the selector.
12. **Records.** Every selection emits a `tool-selection-record-v1` record. It holds the role, mission type and id, matrix version, digest and threshold, registry version and digest, request digest, disposition, failed step, route, needs and unmet needs, and per candidate the outcome, step, rule, reason, signals, score and route. It also holds the pre-fallback surface, the admitted surface and the fallback records. `records.reconstruct_surface` recomputes the surface from the per-tool outcomes. `records.record_problem` checks that a record is consistent. The same inputs always give the same record, because there is no timestamp.
13. **EPAP link material.** `records.link_material(record)` returns the `signed` part of an `epap.links` link named `TOOL_SELECTION`. Its materials are the canonical matrix, registry and request (`tool_selection/{matrix,registries,requests}/<sha>.json`). Its products are those plus the record (`tool_selection/records/<sha>.json`). Its byproducts are the record. It is not signed here: signing and pack assembly belong to the live enforcement wiring, which is outside this leg.
14. **Descriptions are never interpreted.** A registry entry may carry a `description`. It is checked to be a string and is otherwise ignored, because tool descriptions are attack surface (doctrine §5.1).

# RUNTIME-TOOL-BINDING-SPEC-001 — A2 implementation decisions

**Mission:** M-EPAP-TOOLWIRE-002, round 1
**Built from:** `missions/M-EPAP-TOOLWIRE-002/PLAN.md` (the spec's operative content). The dispatcher half, `mission_dispatch/binding.py` (MISSION-DISPATCH-001 Amendment 011), is read, never changed.

## Layout (added)

| File | Role |
|---|---|
| `runtime_binding.py` | `bind(seat, runtime, mission, checkout, session_path, evidence_dir, gateway_root, now) -> Binding`, `BindingRefused` |
| `seats.json` | Seat → role, mission type, fabric role, principal, gateway resources (`mission-seats-v1`) |
| `runtime_registry.json` | The `tool-registry-v1` registry of runtime tools the dispatcher can grant |
| `matrix.json` | `doctrine-s4-v2`: HITL decision D2 only |
| `../tests/test_runtime_binding.py` | Vectors P1-P7 (with P4a, P5a) as `test_vector…`, plus hardening cases |

## Resolutions

15. **One registry name per runtime grant.** The registry rejects a name that appears twice, so the second `Write` (scoped to the mission's reviews) is registered as `Write:reviews`. A registry name maps to a runtime tool by the part before `:`; gateway tools are registered under their full runtime name `mcp__governed-retrieval__<tool>` and bound as the bare tool name. An admitted name that maps to neither a built-in tool (`Read, Edit, Write, Glob, Grep`) nor a gateway tool refuses the binding.
16. **Resources.** The registry's one repository is `checkout`. Built-in tools and gateway tools have path `.` (the gateway reads its corpora from the checkout it is started on). `Write:reviews` has path `missions/{mission_id}/reviews`; the binder puts the mission id in before selection, and the rendered registry is what the selection and the audit record see. Mission ids are limited to letters, digits and `_ . -`, so the path and the rule stay inside the checkout.
17. **Selection request.** The binder builds one request per bind: `request_id` `<mission>.r<round>.<seat>`, the seat's role and mission type, `authority_ref` `MISSION-ROUTER-001`, repo `checkout`, read scope `.`, write scope `.` on a mutation-capable row and none on a read-only row. The needs are the capabilities the registry offers that the row admits: a seat needs its whole admitted runtime surface. The mission's `build_scope` is not narrowed into rules. The dispatcher enforces it on the change, it is recorded in the audit, and P1 fixes the writer's rules at `Read(**)`, `Edit(**)`.
18. **Only ADMITTED binds.** Any other disposition (`BOUNDED_CLARIFICATION`, `NO_TOOL_REQUIRED`, `STOP_AND_FAIL_CLOSED`) and any inconsistent record refuse. Fallback cannot widen the surface, so it is refused rather than bound narrowed. Matrix or registry defects are refusals too.
19. **Rules from classes.** A read-class admitted built-in gives `Read(<glob>)`, a draft- or write-class one `Edit(<glob>)`. The glob is `**` for path `.` and `<path>/**` otherwise. Rules are deduplicated, `Read` rules first. `denied_rules` is empty: the dispatcher's own denials and ceiling stand, and the binding adds none.
20. **Monotone by construction.** Every bound tool comes from an admitted registry entry. The binder also checks that the set of bound registry names is a subset of the selection's admitted surface, and refuses otherwise.
21. **Gateway check.** Every admitted gateway tool must be in `<gateway_root>/mcp_gateway/tools.json`, the catalog of the tooling tree the dispatcher starts the gateway from. A missing or unreadable catalog, or a tool it does not serve, refuses the binding.
22. **Session.** Exactly the `mcp_gateway/session.py` fields: `principal`, `role` (fabric role) and `resources` from `seats.json`, `acting_identity` = `mission["agent"]` (refused unless it equals the seat's principal), the mission block with the constant `authority_ref` `MISSION-ROUTER-001`, `issued_at = now`, `expires_at = now + 3600`. The binder writes no file. A `session_path` or `evidence_dir` inside the checkout (by absolute or resolved path) is refused.
23. **Inputs checked before selection.** The runtime must be `claude-code` or `cursor-cli`. The seat must be in `seats.json`. The mission must have exactly `id, round, agent, base_sha, build_scope`, with a round of at least 1 and a 40-hex lowercase `base_sha`. `now` must be a non-negative integer. Both runtimes get the same surface; the runtime is recorded.
24. **Audit.** `audit` is the `signed` part of an `epap.links` link named `RUNTIME_BINDING`. Its materials are the canonical matrix, rendered registry, request and seat table (`tool_selection/{matrix,registries,requests,seats}/<sha>.json`). Its products are those plus the selection record and the binding document (`tool_selection/{records,bindings}/<sha>.json`). Its byproducts are seat, runtime, role, mission type, matrix version, the full selection record (per-tool outcome, rule and reason) and the binding (tools, rules, gateway tools, the registry-name-to-runtime-tool map, the session). It is not signed here: the dispatcher records it.
25. **Matrix D2.** `matrix_version` is `doctrine-s4-v2`. The writer `admit` list gains `repo_read`, `doctrine_lookup`, `corpus_search`, `citation_extract` and `artifact_lookup`; the reviewer `admit` list gains `corpus_search`, `citation_extract` and `artifact_lookup`. Nothing else changes. Four existing `test_tool_selection.py` cases asserted v1's disjoint writer and reviewer rows. Their expected values are updated to what D2 implies (the writer now also admits the fixture's two read-class tools); no test logic changed.
